Обсудили:

1. Архитектура и разграничение зон ответственности — зафиналены. Договорились, кто на какой стороне выполняет вычисления. Бэкенд поднимает сервис аналитики, который принимает входящие ивенты и складывает их в ClickHouse.
2. Ключевой блокер — недостающие параметры от ML-команды. Для рекомендательной системы нужна категоризация постов (о чём пост) и язык контента. Ранее обсуждали, что это будет делаться на этапе модерации, но по итогам отдельной встречи с генеративными командами решили: категоризация происходит на шаг раньше — в момент генерации контента, а не на модерации. Работа уже в процессе со стороны аудио/бэка.
3. Ресурсы бэкенда — не блокер. Иван подтвердил: ресурса достаточно, чтобы поднять сервис аналитики и сделать доработки по отправке ивентов, можно брать с высоким приоритетом. Отдельно поднят вопрос по ClickHouse — Бахридин дал добро стартовать разворачивание инфраструктуры уже сейчас (запрос к DevOps), чтобы не блокироваться позже.
4. Три этапа работы согласованы:
   4.1) сбор аналитики
   4.2) обработка данных на стороне Recsys
   4.3) интеграция для получения рекомендательной ленты. Егор предложил делать 2 и 3 параллельно с 1, поскольку контракт ручек можно прорабатывать независимо от готовности данных.
5. Модель данных — на финальную проверку. Николай скинул документацию (модель данных, открытые вопросы, последнее обновление 21 июля). Egor берёт на себя сверку: подтвердить/скорректировать по трек-мете, пост-мете, юзер-фичам — в приоритете первыми эти три таблицы. Отдельно нужно добавить трекинг для аудио: с какой секунды пользователь ушёл/сколько прослушал (по аналогии с тем, что уже трекается для изображений/лайков) — потребует ивента с клиента, доп. доработка на стороне бэкенда.
6. Расчёт ресурсов на RunPod — представлен Бахридину. Два компонента: поисковый индекс (эмбеддинги для поиска кандидатов, обязательный) и вычисления под модель для онлайн-обновления рекомендаций. Ориентир — около $10 в день суммарно. Бахридин забирает расчёт для согласования бюджета с Тимуром. Важный риск, зафиксированный отдельно: расчёт актуален для запуска на RunPod, но в будущем сервис потребуется переносить на инфраструктуру клиента (AWS) — под это нужно закладывать дополнительные серверные мощности. Бахридину направлена таблица с этим комментарием.
7. Логика формирования ленты — согласована. Две отдельные выдачи: аудио и посты. Офлайн-пресет (заранее посчитанный, ~100 треков) + онлайн-досчёт по партициям по мере потребления контента пользователем, с учётом реакций текущей сессии. Полная гарантия «без пустой ленты» невозможна при агрессивной перемотке, но это общепринятое ограничение.
8. Формат выдачи — уточнён. На выходе от Recsys нужен только список ID (без самого контента) — бэкенд дополнительно фильтрует приватность и подмешивает рекламные посты. Рекомендательная система должна уметь отдавать гибкое количество ID по запросу (не фиксированное число), чтобы бэкенд мог компенсировать нехватку рекламных постов.
9. Открытые вопросы, вынесенные на уточнение у Бахридина (через Николая):
   9.1 Нужно ли подмешивать в ленту посты по подписке (следующая/подписчики) — Recsys сейчас это не учитывает (нет графа и истории взаимодействий). Предложение — отложить на вторую-третью итерацию, сейчас сделать базовую версию только на основе интересов.
   9.2 Нужно ли на стороне Recsys подмешивать новые/популярные посты, или отдавать чистую рекомендательную выдачу как есть.
10. Ограничение по жанрам аудио — подсвечено повторно. Сейчас захардкожено 14 жанров, кантри отсутствует, хотя занимает топ-4 позиции в США — основном рынке. При запросе country модель пытается сымитировать что-то похожее вместо явного отказа. Доработка жанровой модели нужна, но не сейчас.
11. Резервный сценарий на случай недоступности ML-сервиса — Николай зафиксировал вопрос, нужно продумать поведение системы (что делать, если Recsys не отдаёт данные или отдаёт неполный список).
